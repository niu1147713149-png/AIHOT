# AIHOT 原站功能对照与本地实现评估

研究日期：2026-10-12（Asia/Shanghai）。研究对象为 [aihot.news](https://aihot.news/) 与本机的「AI机会雷达」。

后续实施记录：本报告完成后，已按新委托同步上游并部署 `931a4eb`，见[升级记录](upstream-upgrade-20261012.md)及[二次开发任务](development-roadmap.md)。下文“本地版本 / 状态”保留研究阶段的快照，不代表升级后的现状。

**结论：原站公开可见、而本地缺失的主要功能，都有可行的本地实现路径。部分只需升级开源引擎，部分需要新增模块。原站的全部历史数据、完整信源配置、冻结评分参照组和私人后台，不能从现有开源仓库直接取得，因此不能承诺内容、评分和后台与原站完全相同。**

本报告是研究与实施方案；本次没有升级运行中的应用，没有修改现有信源或提示词，没有安装远端 Skill，没有新增定时采集或付费模型调用。

最新上游仍明确说明模型榜、重置监控和主题大事记只留在原站；升级不能带回这些模块。本地历史迁移 `0053_drop_leaderboard_monitor.sql` 已明确撤掉相关表和状态，也不能靠改开关恢复。

## 4. 各个缺失模块怎样实现

### 4.1 模型榜、证据详情与价格

[模型榜](https://aihot.news/leaderboard) 当时显示 35 项参与计分的评测、7 家机构；[来源目录](https://aihot.news/leaderboard/sources) 列出 90 项已审查来源与专项。这不是让一个 LLM 给模型打分的页面。

建议新建 `modules/model-leaderboard/`，按以下数据层实施：

1. **模型档案**：稳定 ID、厂商、别名、版本、发布日期、上下文、开放权重链接、许可与可用地区的证据。
2. **评测证据**：来源、基准版本、原始分数、推理档位、Agent／工具配置、采集时间、上游数据时间、采用／排除原因。
3. **价格快照**：输入、输出、缓存命中、币种、计量单位、官方页面、核验日期、汇率日期；缺价与零价分开。官方价格和用户实际使用的 JarlessAPI 渠道价格分别保存。
4. **计算与发布**：榜单版本、数据完整度、缺测状态、排名资格、有效快照、各类榜、模型页和来源页。
5. **维护后台**：别名合并、异常价格审核、失效来源、重算与结果差异预览。

第一阶段可先用明确来源的少量模型与评测，做可追溯的选型表、原始成绩对照和价格比较。接入现成评测结果通常比自己运行完整基准节省投入；具体数据源的 API 可用性、额度和费用仍需在接入时逐个验证。

[原站评分规则](https://aihot.news/leaderboard/rules) 已公开 IRT 类型的方法，权重为编程 40%、科研 20%、专业办公 20%、知识问答 15%、真人盲选 5%，并涉及固定代表配置、同类评测归并、截尾读数、异常值限制、分层收缩和排名覆盖条件。页面当时标注方法版本 `2026.10-capability-scale-v19`，还有 92 个模型构成的冻结参照组。

**同类评分方法可以实现；原站完全相同的分数仍需要相同的输入矩阵、别名与配置规则、冻结参照组和校准快照。** 本次未取得完整生产数据和拟合实现，不应把新计算的分数冒充原站分数，也不能用一个简单加权平均声称复现其 IRT 体系。

验收重点：同输入与方法版本可重算出同结果；真实 0 分不当缺测；相近型号不混用；价格缺失有明确状态；每项分数可追溯；评分与价格更新分别计时；采集失败显示数据陈旧程度。

### 4.2 性价比「斩杀线」

[2026-10-06 更新说明](https://aihot.news/changelog) 明确写到：按评分和场景价格画散点图，用帕累托前沿连接“没有更便宜且更强替代品”的模型；可看缓存后的价格明细及替代模型。

这部分计算完全可以本地实现。一个透明的成本口径是：

`成本 = [输入 tokens × ((1 − 缓存命中率) × 输入单价 + 缓存命中率 × 缓存单价) + 输出 tokens × 输出单价] / 1,000,000`

单价均按每百万 tokens，且币种统一。缓存写入、存储、长上下文阶梯价、批处理和渠道折扣需要单独说明，不能默认已包含。

在同一场景下，若另一个模型价格不高且评分不低，并至少一项严格更优，则当前模型不在前沿。价格或可比分数缺失时不参与该计算。数据来自不同测试版本时，先解决可比性再画线。

对本站可以增加缓存比例与输入／输出比例选择，帮助估算国内工具服务或自动化任务成本；这是建议扩展，不是已核验原站具有的全部交互。原站实际场景系数尚未在本次点击验证，不能声称已精确复现。

### 4.3 主题大事记与公司编年史

[OpenAI 主题](https://aihot.news/topics/openai) 展示历史编年史；[Agent 主题](https://aihot.news/topics/agent) 展示重要进展时间轴；[教程主题](https://aihot.news/topics/tutorials) 以精选列表为主。

本地已有主题归属、事件与报道时间线，也预留了主题页模块接口。建议新增 `modules/topic-milestones/`：

- 条目保存主题、事件日期及精度、类型、标题、原始证据、关联事件／文章、复核状态。
- 公司页分模型与产品／公司事件；技术页按重要进展排序；教程、观点等页无需强加时间轴。
- 新候选从已归组的事件产生，经规则或人工确认后展示；相同事件只保留一个里程碑。
- 发布撤回、主题归属更正、日期更正时同步更新，避免旧时间轴继续展示错误内容。
- 更早历史由官方发布等证据补录。本地目前的几百条资料无法自动生成原站多年的完整编年史。

这是最符合本站“看懂变化、发现国内应用机会”的补充之一：适合跟踪产品开放、价格变化、商用条件和关键工作流更新。首版可用现有数据与人工补录，未必需要新增模型调用。

### 4.4 Tibo 重置监控

[原站页面](https://aihot.news/codex-reset) 跟踪的是 Tibo 的公开重置和发卡消息，不是某个用户账号的实时余额，也不能替用户执行重置。

可以选择两条路线：

| 路线 | 做法 | 条件与维护 |
|---|---|---|
| 本地研究用读取端 | 对接原站公开 `codex-resets/recent`，展示日历、原帖、预告／确认和监控状态 | 按原站建议至少间隔 10 分钟，保存 ETag；只在需要完整历史时读取完整接口；依赖原站数据与可用性 |
| 独立监控 | 通过合适的公开 X 数据服务收集公告，抽取日期、对象和事件类型，关联预告与确认 | 需要采集服务、时区解析、事件去重、人工复核；产生持续维护与可能的服务费用 |

实际接口已核验含 `events`、`activities`、`monitor`、`checkedAt` 等字段。查询时原站 `monitor.status=attention`，最近完整核验与最近采集时间不同，说明本地展示必须保留“待处理／未完整核验”的状态，不能把一次请求成功当作业务已核实。

验收重点：发卡不等于额度恢复；预计时间经过不等于官方确认；夏令时和北京时间正确换算；保留原帖和确认依据；同一公告不重复通知。通知目标和启用范围需要另行配置。

### 4.5 本站 Agent Skill

[原站 Skill 说明](https://aihot.news/aihot-skill/README.md) 已公开；其核心是让 Agent 查询服务端的 Markdown，而本地 `/api/v1/agent` 和 7 个 MCP 能力已经存在。

可编写指向 `http://localhost:3080/api/v1/agent` 的「AI机会雷达」Skill，提供查询示例、来源引用、时间口径、安装与卸载说明，必要时再提供校验清单和安装脚本。查询读取已有发布内容，不需要为每次阅读重新让本站模型分析。

使用本机 Agent 时可以访问 localhost；云端 Agent 或另一台设备不能直接访问这台电脑的 localhost。后者需要后续确定可达的部署地址。本次不要求公网发布。

## 5. 内容量差距及真正需要补的输入

以下是页面当时的统计快照，不是固定指标：

| 指标 | 原站 | 本地 |
|---|---:|---:|
| 信源 | 878 | 21 |
| 类型分布 | X 502、RSS 184、网页 145、公众号 23、接口 24 | RSS 21 |
| 收录 | 约 42.8 万 | 360 |
| 精选 | 4,479 | 59 |

原站计入热度的来源不一定都向读者发布文章，不能把 878 理解成 878 个完整转载频道。本地已支持 RSS、网页列表、JSON、X、公众号与推送接入等方式；当前 X、公众号相关第三方凭据未配置，飞书推送关闭。新增名单不会凭空带回原站的运营历史。

对国内个人和小团队，建议优先补高价值的官方产品更新、开发者实践、定价与商用许可变化，再按产出和噪声调整。原站的完整 878 源清单不在开源库中，盲目追求相同数量会增加采集和模型成本。

本地内容较少还受到运行时间短、Docker 曾停机、现有筛选口味与门槛、来源更新量影响。不能仅凭数量推断采集程序损坏；这次没有开展逐源健康修复或重新评估全部历史内容。

## 6. 原站数据与开源代码是不同的使用范围

开源框架是 MIT 许可，作者明确要求使用自己的站名和 Logo。原站的[公开使用规则](https://aihot.news/terms)另行约定服务数据：个人非商业、公益及组织内部研究可按规则免费使用；对外商业产品、客户交付、公开镜像或数据转售需要原站书面授权。

因此，当前本地研究可以评估公开接口；如果以后把依赖原站持续数据的版本对外提供服务，要先处理相应授权与第三方内容条件。独立开发功能、采用自己的来源和数据，是另一条实施路线。本次没有发出联系消息，也没有部署原站数据镜像。

## 7. 建议实施顺序与验收

| 顺序 | 交付范围 | 理由 | 关键验收 |
|---|---|---|---|
| 第一步 | 升级开源引擎，保留站名、国内应用取向、21 源和现有模型 | 先获得已有功能和修复 | 配置与数据备份；合并 `NAV` 等新配置；类型、后端、前端和 smoke 检查；关键页面复核 |
| 第二步 | 主题大事记、本站 Skill、小范围模型资料与价格表 | 直接帮助理解趋势和工具选型；可以分小批交付 | 证据链接、日期、来源更正与撤回；本机 Agent 能正确查询；价格口径可追溯 |
| 第三步 | 多来源评测、模型详情、分领域榜及性价比图 | 形成完整模型选型功能 | 数据获取稳定；模型别名与评测配置正确；评分可重复；前沿计算和缺测处理通过检查 |
| 第四步 | 按需补 Tibo 监控、更多社交信源和通知 | 个人工具价值与采集成本需结合实际使用 | 时区与事件状态、陈旧数据提示、去重、限流、通知对象和频次 |

模块应接入现有 `site/modules/index.ts`、`server.ts`、`web.ts`：后端定时任务、队列、模型步骤、主题页、公开页面、导航和 MCP 都有扩展接口。新增表使用新的模块迁移；不修改旧的 `0053` 迁移，不把原站已移除的旧表直接塞回生产。

数据读取遵循统一发布层，付费调用继续经过回执和预算机制。新增模块需要自己的行为测试；上线到本地前执行 `npm run typecheck`、独立测试库的 `npm test`、前端构建与相关浏览器测试、`node scripts/smoke.ts --base http://localhost:3080`，并补充新路由与数据刷新验收。本次是研究报告，没有改应用代码，因此未重复运行这些代码验收。

## 8. 实施前仍需选定的事项

- **第一批范围**：按上面的建议分阶段，或明确先要模型榜／重置监控中的某一个。
- **数据路线**：自己维护模型与评测数据，还是在原站规则允许的范围内使用其数据。模型榜目前没有公开 API，不能假定所有功能都可通过接一个接口获得。
- **持续投入上限**：目前没有明确金额预算。需要在接入付费 X 数据、评测数据或扩大模型处理前确定；现有请求次数熔断不等同于月度金额预算。
- **精确复现要求**：功能和体验接近可以规划；要求每条历史内容、每个分数与原站完全相同，则需要原站额外提供数据和配置。

域名、运营主体和对外上线继续按用户此前决定暂缓，不影响本地开发评估。
